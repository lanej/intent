# Native approval activation

Intent's `intent lifecycle inventory|checkpoint|restore|verify|stop` command inspects or controls one existing local profile service or paired remote broker. Supply `--profile PATH` for a local service or `--directory DIR` for a remote broker. `intent lifecycle profiles` returns the validated existing profiles without configuring SSH or opening a connection. Unknown legacy controls return incomplete activation and leave the process intact.

The owner-native JSON contract is version 1. Each target reports the selected embedded build identity, the build identity compiled into the running image, PID, operating-system process start identity, native incarnation, readiness, and session restoration evidence. Approval services own no conversation session, so their session list is empty. The owner build entrypoint embeds a unique image identity and separately records executable SHA-256 for transfer validation. Pathname changes cannot rewrite the running identity; unmanaged builds report it unknown.

A checkpoint requires the exact inventoried process tuple and a UUID operation ID. The service fences new approvals, cancels admitted calls, and waits up to 59 seconds for their handlers to confirm exit. It records interrupted request IDs with outcome `interrupted-or-unknown`; it never repeats an approval or an application operation. A failed or pending checkpoint preserves the process. A repeated request for the same retained checkpoint observes that checkpoint without cancelling again; a conflicting operation is refused.

`stop` is accepted only after a matching confirmed checkpoint and closes restoration irreversibly before returning its reply. New approvals remain fenced while the service exits; repeating stop observes the acceptance without another shutdown. `restore` removes an unconsumed fence on the same process without replaying interrupted approvals. Restoring an old checkpoint consumes its operation ID, and subsequently using that ID to request cancellation is refused.

Local and remote approval sockets, Mac routing IDs, transport sockets, and existing SSH connections remain owned by the existing forwarding configuration. Lifecycle requests travel over the private owner endpoint and bypass native authentication without granting approval authority. Requests from an older binary that cannot implement this lifecycle contract must remain running until a trustworthy checkpoint path is available.

`intent lifecycle stage --directory DIR --sha256 HASH` installs a supplied platform binary into the paired broker's private content-addressed releases, without changing its socket or stopping its process. `restart` requires the retained confirmed checkpoint, stages its executing selected binary immutably, ends the old service through its native control, and launches one replacement with the retained profile or Mac routing ID. Private operation receipts record stop and launch intent before either effect. Receipt and log paths are namespaced by the stable endpoint identity, so distinct local profiles can share an update UUID and duplicate aliases still identify one broker. A retained ambiguous operation permits inspection, never a second launch. `lifecycle artifact` reports the image identity compiled into the CLI separately from the selected file SHA-256. It returns a SHA only when the adjacent owner build manifest binds that compiled identity to the opened binary bytes; a changed mutable pathname cannot pair an old executing identity with new bytes.

`make install` publishes the verified build and its manifest in a private content-addressed release, makes both read-only, and atomically selects the release through the installed launcher link. Recognized previous native binaries are preserved. The builder fingerprints its own implementation, module and package inputs, embedded assets, compiler settings, and target platform before and after compilation. Transfer SHA receipts remain separate from native running-image identity.
